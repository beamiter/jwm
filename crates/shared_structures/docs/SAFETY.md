# 安全说明

本文说明 `shared_structures` 0.3 的安全边界、并发保证和应用必须遵守的运行条件。协议布局参见 [架构设计](./ARCHITECTURE.md)。

## 平台与参与者

- 仅支持 Linux。
- 共享同一映射的进程必须使用协议 v12、相同端序和兼容的目标架构（32/64 位混用或跨架构容器共享同一映射不受支持；槽位校验和使用本机字节序，版本常量隐式承载 ABI 变更）。
- feature 可以不同，但每个 opener 必须编译创建者选择的同步后端。
- 共享内存参与者属于同一信任边界。本库会验证初始 header 和每个读取槽位，但不能防御另一个恶意进程在校验后任意改写映射。

不要把可由不受信任用户替换的 flink 路径当作安全 IPC 端点。应用应使用权限受控的目录，并自行处理身份验证和授权。

## 安全 API 的实现不变量

实现中的裸指针和 `unsafe impl Send/Sync` 依赖以下不变量：

1. 映射在任何派生指针使用期间保持存活；
2. header 的 magic、版本、总长度、容量、backend id、槽大小和布局标记已验证；
3. 每个偏移用 checked arithmetic 计算，且完整区域落在映射长度内；
4. wire 类型只包含任意位模式均有效的字段，领域类型只由已验证 wire 值构造；
5. 同一方向上的生产者或消费者在访问槽位前持有对应共享方向锁；
6. 写入完整槽位后才以 Release 发布索引，读取者以 Acquire 观察索引；
7. backend header 的地址满足其对齐要求，并与 header 声明的 backend 一致。

创建者不会把 flink 直接指向初始化中的映射。通用 header 和后端对象构造完成、magic 发布后，才通过原子硬链接公开 flink；因此普通 opener 与初始化写入之间不存在发布期数据竞争。

修改内存布局、锁顺序或原子内存顺序时，必须重新审查这些不变量。不得仅依靠注释把可能导致未定义行为的调用者约束放到安全 API 上。

## Wire 类型与固定大小复制

公开的 `SharedMessage`/`SharedCommand` 是领域值；共享内存使用独立 wire 表示。尤其是布尔状态在 wire 中编码为整数位，读取时验证后再转成 Rust `bool`。这样，损坏字节不会被直接解释成无效的 Rust 值。

队列操作会复制固定大小槽位。返回的消息不借用共享映射，句柄或槽位随后变化不会使该值失效。这也意味着当前 API 不是零复制。serde 与 rkyv trait 实现不参与共享队列协议，不能据此推断 wire 兼容性。

泛型 `TypedRingBuffer` 在 header 中记录槽位类型指纹（`WireSafe::FINGERPRINT`，默认哈希类型名）并在打开时校验，可拒绝"槽大小相同但类型不同"的错配打开。指纹是防错配自检，不是安全边界：同名同路径但字段重排的类型检测不到；跨 crate 共享同一布局的类型需要两侧覆写为同一指纹常量。布局纪律最终由使用者负责。

字符串字段具有固定字节容量。setter 会保留结尾零字节，并退回到最近的 UTF-8 字符边界后截断，因此经 setter 写入的过长字符串仍是合法 UTF-8，但不会原样往返。该规则同样适用于最小化窗口 title 和 app-id/class。直接修改公开字节数组可能产生非 UTF-8 数据；lossy getter 会替换无效序列。若应用要求拒绝截断，应在写入前自行检查编码后的字节长度。

## 并发模型

消息和命令各有独立的写锁与读锁，因此多个进程或线程可以同时调用相同方向的安全 API。锁按单次操作持有，不跨用户回调，也不在阻塞等待期间持有。消息方向与命令方向互不串行化。

该设计在语义上支持 MPMC，但实现针对无竞争 SPSC 优化：每个方向只有一个生产者、一个消费者时可以避免锁竞争；三个后端在无人等待时都会避开通知 syscall。高竞争 MPMC 工作负载会被方向锁串行化，不应期望随生产者数量线性扩展。

状态查询和 `stats` 是瞬时快照。即使刚观察到“非空”或“未满”，另一个参与者也可能先完成操作；调用者必须处理 `None`、full、timeout 或 closed 结果。

## 方向锁的崩溃恢复语义

共享方向锁的锁字存放持有者 PID。持有者进程消失（`SIGKILL`、崩溃、`abort`）后，竞争者通过 `/proc/<pid>` 探测发现并原子夺回锁，因此单个参与者崩溃不会永久卡死方向。前提与已知边界：

- **所有参与进程必须共享同一 PID namespace 并看到同一个 `/proc`**。跨 namespace 部署（容器间共享映射）时，持有者的 PID 在观察者的 `/proc` 中不存在，锁竞争会把活着的持有者误判为已死并夺锁，造成双持有者。`/proc` 完全不可用时探测自动退化为"假定存活"（纯等待，不夺锁），但跨 namespace 且各自挂有 `/proc` 的场景无法自动检测，必须由部署保证。
- **僵尸进程视为已退出**：Linux 会在父进程 `wait` 前保留僵尸的 `/proc/<pid>` 目录，但僵尸已经不能执行用户代码或释放锁。探测会读取 `/proc/<pid>/stat`，把 Z/X/x 状态视为已死；stat 不可读或无法解析时则保守地假定存活。
- **PID 复用**：探测可能把复用了同一 PID 的无关进程误判为"持有者仍存活"，此时行为退回等待。反方向的误夺（探测到已死后、CAS 之前，锁恰好被释放又被一个复用了相同 PID 的参与者取得）在理论上存在，概率极低；对正确性要求极端的部署应配备外层监督与重建机制。
- **半写槽位**：写入者在槽位复制中途死亡时，被夺锁后的消费者会读到校验和不匹配的槽位并将其作为损坏数据消费掉；该消息丢失但队列继续工作。

不要在临界区内执行可能阻塞的外部操作。Rust panic 路径必须通过 RAII guard 释放方向锁。任何新增的提前返回或错误分支都必须经过同一 guard。

## 等待、超时与通知

Futex、Semaphore 和 EventFd 都允许伪唤醒、中断或“通知已发生但其他消费者先取走数据”。正确模式始终是：

1. 检查队列；
2. 若无数据则等待；
3. 被唤醒后重新检查；
4. 直到成功、超时或映射关闭。

通知发生在数据提交之后。提交成功但通知 syscall 失败时，数据仍属于队列；API 不应把这种情况报告成可安全重试的“未发送”。轮询或后续通知仍可让消费者发现该数据。

Futex、Semaphore 和 EventFd 都用共享 sequence 和 waiter 计数完成 SeqCst 注册握手。signal 无论是否进入内核都会推进 sequence；waiter 在登记前后比较 sequence。因而 producer 要么看到 waiter 并发出通知，要么 waiter 看到 sequence 已变化而不睡眠。destroyed 状态与广播计数使用同样的全序规则，避免关闭注册窗口中的永久睡眠。

超时是调度承诺，不是实时系统保证。调度延迟、系统调用中断和多个消费者竞争都可能让实际返回时间略晚。

## 生命周期

- opener 的 Drop 只分离当前句柄并关闭本地后端资源。
- creator 的 Drop 执行拥有者清理：标记 destroyed、唤醒等待者并移除 flink。
- `destroy` 是显式全局关闭；调用开始前已经通过最终 destroyed 检查的并发写操作仍可能完成，随后发起的写入会被拒绝，等待者应尽快返回 closed。
- 移除 flink 只阻止新的 opener；已经映射的进程仍持有其映射，必须通过 destroyed 状态协调退出。

创建者意外退出会触发普通进程析构的前提只适用于正常展开；`SIGKILL`、`_exit`、断电或进程 abort 不运行 Drop。header 记录 `creator_pid`，`creator_alive()` 可通过 `/proc/<pid>/stat` 探测创建者是否仍存活（尚未被 `wait` 的僵尸也判定为已退出）；`SharedRingBufferOptions::reclaim_stale(true)` 让 `open_or_create` 在确认创建者已死后移除残留 flink 并重建映射。回收应只由单一监督者角色执行：多个进程并发回收同一路径可能互相删除对方刚发布的 flink；PID 复用会让回收退化为打开旧映射（安全方向）。

## EventFd 特有条件

EventFd 后端由创建者生成两个 eventfd，并通过 Unix domain socket 向 opener 传递文件描述符。socket 位于属主私有（0700）目录内（优先 `$XDG_RUNTIME_DIR`），创建者用 `SO_PEERCRED` 校验对端有效 UID，拒绝其他用户的连接。创建者必须存活且监听 socket 可访问，新 opener 才能完成连接；创建者关闭后，新 opener 得到明确的 `NotConnected` 错误。收到的 FD 只用于唤醒，队列数据仍从共享映射读取。

现有 opener 已持有自己的 FD 副本。创建者销毁时会设置停止标志、主动唤醒并 join 监听线程、移除 socket，然后关闭其本地 FD；普通 opener 的 cleanup 不得停止创建者的监听线程。其他进程必须根据 destroyed 状态结束等待和访问。

## 应用检查清单

- 使用权限受控、不会与无关程序冲突的 flink 路径。
- 所有参与者协调升级到同一协议版本。
- 显式选择已编译的同步后端，或使用 `open_auto`。
- 把 full、empty、timeout 和 closed 当作正常并发结果处理。
- 不依赖 stats 快照进行正确性判断。
- 在创建者退出前停止生产并排空需要保留的数据。
- 对崩溃恢复要求较高的系统，在外层增加监督、心跳和映射重建机制。
